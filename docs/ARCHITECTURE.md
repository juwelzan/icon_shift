# Architecture

## Repository layout

```text
icon_shift/                     Flutter plugin (runtime), published as icon_shift
├── lib/
│   ├── icon_shift.dart         public API (exports only)
│   ├── icon_shift_platform_interface.dart   for implementers and tests
│   ├── icon_shift_web.dart     web implementation
│   └── src/
│       ├── icon_shift.dart     IconShift static facade
│       ├── engine.dart         IconShiftEngine: all policy
│       ├── theme_sync.dart     opt-in brightness → variant sync
│       ├── config/             IconShiftConfig, AppIdentity, resolution
│       ├── models/             results, state, capabilities, property table,
│       │                       application info, preview, diagnostics
│       ├── validation/         configuration validator
│       └── platform/           platform interface, method channel
├── android/ ios/ macos/ windows/ linux/   one native implementation each
├── cli/                        icon_shift_cli: build-time tooling (pure Dart)
├── example/                    demo app (resources generated by the CLI)
├── test/                       Dart unit tests, web DOM tests
└── docs/
```

## Two separate systems

| | Runtime (`icon_shift`) | Build time (`icon_shift_cli`) |
| --- | --- | --- |
| Runs | inside the installed app | on the developer machine / CI |
| Changes | what the OS lets a running app change: alias/alternate icon, window title, favicon… | native project files: ids, names, icons, manifests |
| Effect | immediate (where supported) | after the next build and install |
| Never does | modify bundles, executables, signatures, `.desktop` files | sign, provision, notarize, install |

They share the configuration model (`icon_shift.yaml` → generated Dart
`IconShiftConfig`) and the identity property table, but not code: the CLI has
no Flutter dependency, the plugin no `image`/`yaml` dependency.

### Why a single plugin package (not federated)

All six implementations are first-party and released together. A federated
split would add seven pubspecs for no user benefit. The code is structured
the federated way (`IconShiftPlatformInterface extends PlatformInterface`), so
it can be split later without API changes.

## Runtime layering

```text
app ──► IconShift (static facade)
           │
           ▼
      IconShiftEngine ──── IconShiftConfig.resolve()   (pure, locale-aware)
           │          ├─── validateConfig()            (pure)
           │          └─── identityPropertyTable       (static facts)
           ▼
  IconShiftPlatformInterface   (native keys only)
     │                    │
MethodChannelIconShift   IconShiftWeb (Dart, package:web)
     │
Kotlin · Swift (iOS) · Swift (macOS) · C++ (Win32) · C (GTK)
```

* **Config** is immutable, `const`-constructible data. Resolution is a pure
  function.
* **Engine** owns all policy: validation before applying, capability checks,
  icon-then-name ordering, skip-on-failure, persistence and recovery,
  suggestions on errors. It takes the platform as a constructor argument, so
  it is unit-tested with fakes.
* **Platform interface** is low level: "set icon key `dark` (with these PNG
  bytes)", "set name", "report state / capabilities / issues / app info".
  Native code never parses configuration.

## Resolution

For variant *v* on platform *p*, `name` and `icon` resolve independently;
the first value set wins:

1. `variants[v].platforms[p]`
2. `variants[v]`
3. `defaultIdentity.platforms[p]`
4. `defaultIdentity`

With a locale, each level's `localizedNames` (full locale, then language) is
checked before its `name`. A variant that defines no icon of its own *uses the
default icon*: switching to it restores the shipped icon rather than applying
a copy.

## Results and errors

* **Exceptions** (`IconShiftException`: code, message, operation, platform,
  suggestion) only for programmer errors: not initialized, unknown variant,
  invalid argument, invalid configuration.
* **Results** (`IconShiftResult`: icon + displayName `OperationOutcome`s, plus
  operation and platform) for everything the OS decides. Status is one of
  `applied`, `unchanged`, `pending`, `notRequested`, `unsupported`, `failed`,
  `skipped`; failed/unsupported outcomes carry an `IconShiftErrorCode` and,
  when known, a suggestion.

## Native channel protocol (`icon_shift`)

| Method | Arguments | Returns |
| --- | --- | --- |
| `getCapabilities` | – | `{icon:{…}, displayName:{…}, iconAndNameLinked, notes}` |
| `getNativeState` | – | `{iconKey?, displayName?, pendingIconKey?}` |
| `setIcon` | `{key, bytes?}` (`key` `'default'` restores) | `{status, message?, displayName?}` |
| `setDisplayName` | `{name?}` (`null` restores) | `{status, message?}` |
| `inspect` | `{variants:[{id, hasOwnIcon, name?}]}` | `{issues:[…], info:{…}}` |
| `getApplicationInfo` | – | `{displayName?, applicationId?, version?, buildNumber?, executableName?, windowTitle?, installationType?, osVersion?}` |
| `loadSelection` / `saveSelection` | – / `{selection}` | map / – |

Errors are `PlatformException` codes `unsupported`, `missing_resource`,
`permission_denied`, `invalid_argument`, `not_active`, `native_failure`.

## Build-time pipeline (CLI)

```text
icon_shift.yaml ─► GeneratorConfig.parse (path checks, schema checks)
                         │
            ┌────────────┼──────────────┐
            ▼            ▼              ▼
     resource planners  identity planner  reports (preview, capabilities, doctor)
            │            │
            └─────► Plan (writes, deletes, messages, next steps, diffs)
                         │  --dry-run stops here; any error stops here
                         ▼
                   Backup.create → write → record after-state
                         │
                    rollback restores only files unchanged since
```

Every edit to a template file uses an exact pattern with an expected match
count; a mismatch is an error, never a guess. Generated files carry an
ownership marker and are the only files the CLI deletes.
